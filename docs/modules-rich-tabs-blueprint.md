# Blueprint "Rich Tabs" — tornando cada aba única e útil

## Contexto

Hoje a maioria dos módulos do AgroTorre sofre do mesmo problema: as abas são **genéricas e duplicadas**. Cada aba renderiza o mesmo componente (`ModuleTab` / `ModuleSection` / `CampoModuleSection`) com um `DataTable` (as primeiras 5–6 colunas do `payload`) + um Dialog de CRUD + botões Importar/Exportar. Muda só o nome das colunas — visual e função são idênticos entre Cargas, Motoristas, Rotas, Frota, Estoque, Custos, etc. O usuário não tem KPIs por aba, nem gráfico, nem mapa, nem ação que dispare algo além de editar/excluir, nem link cruzado para o módulo dono da entidade.

**Objetivo:** cada aba deve ser **única e útil** — um mini-dashboard temático com KPIs reais, um visual de domínio (mapa, gráfico, calendário, timeline, kanban) e ações que façam alguma coisa (mudar status, abrir o módulo de origem, gerar uma ordem). Tudo isso **reusando o toolkit que já existe**, sem reescrever o CRUD.

**Toolkit confirmado no codebase (reusar, não recriar):** `DataTable` (com `actions` e `onRowClick`), `StatKpi` / `StatCard`, `charts.tsx` (`MiniArea`, `CashFlowChart`, `TrendLine`, `BreakEvenChart`, `chartColors`), mapas (`AgroMap`, `InteractiveMap`, `MapEntityPanel`, `TrackingMap`), `ui/calendar`, `period-picker`, `recharts` direto para visuais novos (scatter, gauge, Gantt-as-bars, heatmap-as-grid). Metrics já existem: `logistica-metrics.ts`, `pecuaria-metrics.ts`, `equipe-metrics.ts`, `connected-agro-data.ts`.

---

## 1. Padrão reutilizável "RichTab"

Substituir o genérico `ModuleTab` / `CampoModuleSection` / `ModuleSection` por um shell comum de 3 faixas. Criar `src/components/rich-tab.tsx`:

```
<RichTab>
  ├─ <RichTabHeader>      título + ações globais (Importar/Exportar/Novo) + period-picker
  ├─ <RichTabKpis>        faixa de 3–6 StatKpi (derivados de uma fn metrics(records))
  ├─ <RichTabFocus>       slot do visual de domínio (mapa | chart | calendário | timeline | kanban)
  └─ <RichTabTable>       DataTable com colunas ricas + actions úteis (não só editar/excluir)
```

Contrato por aba (config-driven, mantém o CRUD atual):

- `metrics(records) → StatKpi[]` — KPIs reais, não hardcoded.
- `Focus` — componente de domínio (ver tabelas abaixo); recebe `records` + `onSelect`.
- `columns` + `rowActions(row)` — ações que disparam algo (mapa, drill cross-módulo, mudar status), reusando `DataTable.actions`/`onRowClick`.
- `crud` — herda o handler genérico já existente (create/update/delete + import/export). Zero regressão.

Regras transversais (aplicar a **TODAS** as abas):

- **Drill cross-módulo**: toda célula de entidade (motorista, cliente, talhão, lote) é link → abre painel/rota do módulo dono. Usar `MapEntityPanel` como padrão de painel lateral.
- **Estado vazio**: `EmptyState` já existe — usar com CTA contextual.
- **DEMO/real**: manter o gate de `useDemoMode` já presente nos handlers.
- **Cor semântica**: verde/amarelo/vermelho via `chartColors` + tokens `text-success`/`text-destructive`.

---

## 2. Sequência de implementação (impacto × esforço)

1. **`rich-tab.tsx`** (shell + 4 sub-slots) — desbloqueia todo o resto. Validar reaproveitando o CRUD de `ModuleTab`.
2. **2 novos primitivos de visual** reutilizáveis em `charts.tsx`: `HeatGrid` (matriz cor) e `GanttBars` (recharts). `Kanban` e `Timeline` como componentes próprios.
3. **P1 cross-módulo**: Fila de Ações (Torre) + Executivo trending + Cargas/Rotas (Logística) + ROI/Custos (Financeiro) + Pragas/Talhões/Calendário (Campo).
4. **P2/P3** por config, migrando aba a aba (cada migração = trocar `ModuleTab` por `RichTab` + escrever `metrics()` e `Focus`).

Risco-chave: `metrics()` por aba depende de payloads JSON livres (`operation_records.payload`, `field_records`) — padronizar parsers em cada `*-metrics.ts` (já é o padrão) antes de derivar KPIs reais.
